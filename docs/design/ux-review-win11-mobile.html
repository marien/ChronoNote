ChronoNote Win11 & Mobile Review

A review of the desktop app against Windows 11 (Fluent) conventions and of the installed web app against phone conventions (Material 3 on Android, the iOS guidelines on iPhone). Every proposal below is something you can approve, discuss or reject on its own. Nothing is implemented yet.

FrictionlessFewer steps between thought and text. No new mandatory dialogs.
UnclutteredEvery proposal must remove at least as much chrome as it adds.
Keyboard firstNo shortcut changes. Mouse and touch paths should teach the keys.
History close at handPast occurrences should be readable while writing today's note.
Content in focusThe monospace canvas and the glyph language stay as they are.

The review covered docs/spec.md, the style sheets in src/styles/, and the running demo build at 1280×800 and 375×812 (screens captured in Dutch, the default language in my browser). The biggest gaps found:

  • The app chrome is set in the editor's monospace font at 11–12 px. Windows 11 apps use Segoe UI Variable at 12–14 px, so ChronoNote reads like a terminal and is harder to scan than it needs to be.
  • The custom title bar loses Windows 11 behaviour: no Snap Layouts flyout on the maximize button, no inactive-window state, and caption buttons that are not the standard size.
  • The title bar is crowded. Five labelled commands sit next to the tabs, which is why a four-tier collapse system is needed.
  • Phones get the desktop layout, shrunk: no word wrap (text runs off the screen), an 11 px editor, desktop shortcut labels in menus, a 15-button toolbar that scrolls sideways, and a desktop status bar.
  • No support for contrast themes or reduced motion, and secondary text is below the WCAG AA contrast ratio for small text.

A · Foundations

These change how everything looks without moving anything. They are the cheapest way to make the app feel at home on Windows 11, and the rest builds on them.

A1

Two typefaces: Segoe UI for chrome, monospace for the canvas

Now

One font (Cascadia Code) for everything: tabs, buttons, menus, dialogs, the status bar. Chrome text is 11–12 px. In the Dutch UI, "Sectiegeschiedenis" in monospace takes 18 character cells.

Proposed

Add a --font-ui token: "Segoe UI Variable Text", "Segoe UI", system-ui. Use the Windows 11 type scale for chrome: Caption 12, Body 14, Body Strong 14 semibold, Subtitle 20 for dialog titles. The editor, the glyph-rendered rows in drawers, dates in tabs and key hints stay monospace.

A2

Fluent materials: Mica title bar, Acrylic flyouts, standard radii and shadows

Now

Flat VS Code greys (#252526 chrome). Radii vary by component: 4, 5, 6, 8 and 12 px. Overlays share one heavy shadow.

Proposed

  • Mica behind the title bar and status bar on Windows 11 (Tauri windowEffects: ["mica"]). The window is already created transparent for Peek, so this is mostly config. The editor canvas stays a solid colour, so legibility doesn't change. Windows 10 falls back to today's grey.
  • Acrylic (blur plus tint) for flyouts: the date picker, the More menu, the context menu (B5) and tooltips.
  • Two radii: 8 px for windows, dialogs and flyouts; 4 px for buttons, inputs, chips and list items.
  • Two shadows: flyout (8 px blur) and dialog (32 px blur), following Fluent's elevation steps.

A3

Contrast: readable secondary text, contrast themes, reduced motion

Now

  • --muted #858585 on the chrome grey #252526 is about 4.1:1. It is used for 11 px status bar text and footer hints. WCAG AA asks for 4.5:1 for small text.
  • No forced-colors rules. With a Windows contrast theme on (Settings → Accessibility → Contrast themes), the glyph colours and focus rings can disappear.
  • No prefers-reduced-motion rules. The Zen slide, the Peek fade and the jump pulse always animate.

Proposed

  • Split --muted in two: --text-secondary #A6A6A6 (6.2:1) for anything you need to read, and --text-tertiary #858585 only for decoration such as separators and disabled items. Light theme: #5F5F5F on #F3F3F3.
  • A @media (forced-colors: active) block: glyphs use CanvasText/Highlight, open actions keep a visible box, focus rings use Highlight.
  • A prefers-reduced-motion block: switch transitions off and replace them with an instant change.

A4

Fluent motion and focus: one timing set, one focus ring

Fluent uses three durations (83 ms for small changes, 167 ms for flyouts, 250 ms for dialogs) with a decelerate curve on entry. Dialogs scale in from 1.05 to 1.0; flyouts slide 8 px from their anchor. ChronoNote already has a good two-tone focus ring on some controls (v0.29.1). This proposal makes it the only focus style, on every focusable element including tabs, status bar segments and list rows, and moves the timings into tokens so A3's reduced-motion switch can turn them all off in one place.

B · Desktop window and chrome

B1

Title bar behaves like Windows 11: Snap Layouts, caption sizes, inactive state

Now

  • The merged title bar (§154) removed the native one, and with it the Snap Layouts flyout you get by hovering the maximize button. Win+Z still works, but the mouse path is gone.
  • Caption buttons are 44 px wide; the system standard is 46.
  • The bar looks the same when the window is in the background. Windows 11 dims the title bar text and icons of an inactive window.

Proposed

  • Bring Snap Layouts back by answering Windows' hit test (WM_NCHITTEST) with "maximize button" over our maximize button. This is the approach the decorum plugin for Tauri uses; a small Rust subclass in windowChrome is enough.
  • Caption buttons 46 px wide, full bar height. Close turns #C42B1C on hover.
  • Add body.window-inactive, set from the existing onFocusChanged hook: title bar text and icons drop to tertiary, and the active tab loses its accent line.

B2

A calmer title bar: tabs and a + button on the left, icon commands on the right

Now

New scratchpad is an icon among the commands, far from the tabs. Five labelled commands (Date, Actions, Section history, Search, Settings) compete with the tabs for width. To cope, the bar uses four tiers (labels, icons only, scroll arrows, a More button) that change as you resize, with a lot of measuring code behind them (§57, §61).

Proposed

  • A + button directly after the last tab, as in Notepad, Terminal and File Explorer. Click: new scratchpad (Ctrl+N). The ▾ next to it opens: New scratchpad, Open date… (Ctrl+O), Reopen closed tab (Ctrl+Shift+T).
  • On the right, four icon-only commands: Date, Actions, History, Search. Each tooltip shows the name and its shortcut, so hovering teaches the keys. Settings, Shortcuts & symbols, Zen, Peek and About go into a ⋯ menu, as in Notepad.
  • That leaves two tiers instead of four: the tab strip scrolls, and below about 560 px the four icons also move into ⋯.

B3

Notepad-style tabs, with an optional friendly date label

Now

The active tab has a 2 px top accent line and 6 px corners. Inactive tabs have no separators, so a row of grey ISO dates is hard to scan. The past/today/future cue is the icon colour.

Proposed

  • Shape as in Windows 11 Notepad and Terminal: 8 px top corners, the active tab joins the canvas with small outward curves at its base, thin separators between inactive tabs, width between 108 and 200 px, close button always on the active tab and on hover for the others.
  • The past/today/future cue becomes a small dot before the label (grey, accent, green). The colours stay the same, at a quarter of the size.
  • Your call: a "Tab labels" setting: ISO (2026-10-09, today's behaviour) or Friendly (Today, Yesterday, do 9 okt in your locale), with the ISO date in the tooltip either way.

B4

Status bar as Notepad segments, with counts you can click

Now

One dot-separated monospace line: folder, position, words, the three counts, then version, ? and About on the right. The counts are the most useful information but sit in the middle in the lowest-contrast colour. The version and About icon take space on every screen for something you need a few times a year.

Proposed

  • Counts on the left, as buttons: click ☐ 3 open to jump to the next open action (Ctrl+J); click the deferred or done count to open Actions filtered to that state. Messages in the centre, as now.
  • Notepad's order on the right: Ln 13, Col 38 | 62 words | notes | ?, with 1 px dividers and 12 px Segoe text.
  • The version and About move into Settings (C4). An available update shows as an InfoBar (C5), not as an icon.
  • A Show status bar toggle in ⋯ and Settings (Notepad has the same), for people who want only the canvas without going into Zen.

B5

An editor context menu that teaches the shortcuts

Now

Right-clicking in the editor shows WebView2's own browser menu (with items like "Inspect" in dev builds). A mouse user has no way to find Ctrl+1–7, convert-to-section or copy-to-next-occurrence except the palette or the Shortcuts drawer.

Proposed

A Windows 11 style context menu (Acrylic, 8 px corners, an icon row for Cut, Copy, Paste at the top, the same as File Explorer). Below it, the line commands, which change with the line under the caret: action states for an action line, topic states for a topic line, "Make it an action" for plain text. Then: Convert to section, Section history, Copy to next occurrence, Peek on this section. Every row shows its shortcut. The same command list feeds D6 on phones.

B6

Alt key tips on the title bar commands

Pressing and releasing Alt on its own shows a letter on each title bar command, as Office and other Windows apps do: Date, Actions, History, Search, New, More. The next letter runs the command; Esc or any other key hides the tips. Once B2 removes the labels, this keeps every command reachable without remembering shortcuts. The tips trigger only on a lone Alt release with no Ctrl involved, so AltGr typing on US-International is unaffected, and Alt+←/→ (occurrence navigation) keeps working.

C · Drawers, dialogs and settings

C1

History and Actions as a docked side pane next to the note

Now

Section History and Actions are centred dialogs over a dimmed note. While one is open you can't see or type in the note it belongs to. In a meeting you open History, read last week's open points, close it, type, and open it again. The dialog owns the keyboard (§209), which is the right choice for a dialog but makes this back-and-forth slow.

Proposed

  • On windows wider than about 1000 px, Ctrl+Shift+H and Ctrl+Shift+A open a pane docked on the right (about 380 px, resizable), as Outlook's reading pane or VS Code's side bar do. The note stays visible and editable on the left.
  • Focus moves into the pane when it opens, so the keys behave as they do now (arrows, Shift+Enter to add to today). F6 moves focus between note and pane, the Windows standard for panes. Esc closes the pane and returns to the caret.
  • With the pane open, History follows the caret: move to another section in the note and the pane switches to that section's history.
  • Narrow windows, Peek and phones keep today's dialog.

C4

Settings as a page, with About inside it

Now

Settings is a 560 px dialog with tabs and an inner scroll area. Language is an 8-option segmented grid. About is a separate dialog opened from the status bar.

Proposed

As in Windows 11 Notepad: Settings replaces the editor area as a page with a back arrow (Esc and Ctrl+, also go back). Settings are cards in groups (Appearance, Editor, Notes & sync, Peek, Updates), each with an icon, title, one-line description and control. Language and theme become dropdowns, as Windows does for more than three choices. Segmented controls stay where there are two or three short options. The last group is About ChronoNote: version, check for updates, release notes, links. The About dialog and the status bar items go away.

D · Phone (installed web app)

Today the phone gets the desktop layout scaled down. These proposals give it a phone layout while keeping one codebase: they switch on pointer: coarse together with a width under 600 px, the same check $isMobile already makes.

D1

Wrap lines and use a 16 px editor on phones

Now

The editor width defaults to "Full", so on a 375 px phone every longer line runs off the right edge and the note scrolls sideways. The editor uses the desktop default of 13 px. iOS Safari zooms the page in when you focus a text field under 16 px.

Proposed

On phones, the defaults are Wrap and 16 px (the existing hanging indent keeps glyph lines aligned). Both are stored per device, so changing them on the phone doesn't change the desktop and the reverse.

D2

A phone app bar: the date as the title, previous and next on either side

Now

The phone top bar is a shrunken desktop bar: a tab-count button, one desktop-style tab with an ISO date, and three unlabelled icons. Going to yesterday's note takes three taps: the tab drawer, then Open date, then the day.

Proposed

A Material 3 small top app bar. Title: "Today" / "Yesterday" / "do 9 okt", with a subtitle showing the open count. Tap it to open the date picker. ‹ › on either side go to the previous or next note that has content. On the left, the tabs button opens the tab sheet (D4); on the right, ⋯ holds New scratchpad, Zen, Settings and Shortcuts. The desktop tab shape disappears on phones.

See the D1 mockup on the right. A swipe gesture for previous/next day is deliberately left out: horizontal swipes on a text area clash with selecting text and with the system back gesture.

D3

A bottom navigation bar instead of the status bar

Now

Actions, Section history and Search are behind ⋯ in the top corner, which is the hardest place to reach with a thumb. The menu shows desktop shortcuts (Ctrl+Shift+A), which mean nothing on a phone. The bottom of the screen holds the desktop status bar (counts, ?, About).

Proposed

A Material 3 navigation bar with four destinations: Note, Actions (with an open-count badge), History (for the section at the caret) and Search. It replaces the status bar on phones. Line, column and word count are dropped there; the open count lives in the badge and the title subtitle. The bar hides while the keyboard is up, and the accessory bar (D5) takes its place. Shortcut labels are hidden on touch devices everywhere, including menus.

See the D1 mockup. This changes how often History is used on a phone: one tap instead of two, in thumb reach.

D4

Bottom sheets instead of centred dialogs

Now

The tab drawer, the More menu and every drawer open as a dialog in the middle of the screen. They are hard to reach with a thumb and can only be closed with the ✕ or Back.

Proposed

On phones every drawer is a bottom sheet with a drag handle: half height for the tab list and menus, full height for Actions, History and Search. Swipe down or press Back to close (Back already works, §261). Rows are 48 px high. The active tab has an accent bar, as on desktop.

D6

Long-press a glyph for the line menu

Tapping a glyph already toggles it (open ↔ done). Long-pressing the glyph opens a sheet with the same line commands as the desktop context menu (B5): every state, Section history, Copy to next occurrence, Convert to section. Long-press on the text itself keeps the phone's own selection behaviour, so text selection is not affected.

D7

Installed-app details: theme colour, app shortcuts, no pull-to-refresh

  • Theme colour per theme. theme-color and the manifest are fixed at #1e1e1e, so in light mode the phone's status bar stays dark above a white app. Use two <meta name="theme-color" media="(prefers-color-scheme: …)"> tags, and update the tag from script when the in-app theme setting overrides the system.
  • App shortcuts in the manifest (long-press the home screen icon): Today, Actions, Search. Each opens the app with a URL hash the boot code already understands or can be taught.
  • overscroll-behavior: none on the app shell, so pulling down at the top of a note doesn't reload the page and drop the caret.
  • display_override: ["window-controls-overlay"], so when the web app is installed on a Windows PC it gets the same merged title bar as the desktop app instead of a browser-style one.
  • launch_handler: focus-existing, the web-app version of the desktop's single-instance behaviour (§120).

E · What stays, and what I decided against

Stays: the canvasMonospace text, the glyph vocabulary, the setext section rules, plain-text files. All proposals change chrome only.
Stays: every shortcutNo binding changes. B6 and F6 are additions, chosen to avoid AltGr letters and function keys you would need Fn for.
Stays: Ctrl+K, Zen, PeekThe palette is the fastest way to everything; Zen and Peek already behave like Windows 11 compact overlays.
Not proposed: a menu barNotepad has File / Edit / View. It would add a whole row that the palette, ⋯ and the context menu (B5) already cover.
Not proposed: a Fluent component libraryFluent UI Web Components would be a heavy dependency fighting the existing CSS. Tokens and a few patterns give 90% of the look.
Not proposed: a left navigation rail on desktopA rail (as in Mail or Settings) uses permanent width for navigation the keyboard already gives you. C1's pane appears only when asked for.

Suggested order

Release 1: look and feel
A1, A2, A3, A4, B4, C3, D1, D7. Mostly CSS and tokens, low risk; the visual audit specs need new baselines.
Release 2: structure
B1, B2, B3, B5, C2, C5, D2, D3, D4, D5. Title bar, menus and the phone layout. B1's Snap Layouts needs a native check on your machine.
Release 3: bigger changes
C1 (History first), C4, B6, C6, D6. Each is worth a short design round of its own after the earlier releases are in use.

Mockups are drawn in HTML at about two-thirds of real size, using ChronoNote's own dark palette. They show layout and hierarchy, not exact pixels.
