ChronoNote Readiness Review

v0.27 and v0.28 covered the architecture and the code, v0.30 the design. This review looks at what it takes for people other than you to install, trust, keep using and get help with ChronoNote: distribution, recovering from mistakes, knowing what went wrong on someone else's machine, testing what the mock can't reach, and the release process. Features are left out, apart from two that are plainly missing.

Trustworthy to installLicences, privacy and security reporting in order before people ask.

Already solid

For calibration: these are in place and need no work.

  • Atomic writes with a process-wide write lock and retries (§92, §97).
  • Guarded saves: a stale tab never overwrites a newer file; conflict copies in .chrononote-conflicts/ (§94, §291-§293).
  • A corrupt config.json or session file is set aside, not fatal (§97).
  • Zero-loss exit barrier: pending saves finish before the window closes (§93).
  • Path-traversal and symlink-escape checks on every note path (§92).
  • Strict desktop CSP; the test harness provably absent from release builds (CI build guard).
  • 944 unit tests, 657 browser tests, 129 Rust tests; CI on every push.
  • Dependabot, secret scanning, CodeQL, dependency review; signed updater manifests.

The gaps found:

  • Nothing can be undone at the file level. A deleted note, an import "Replace" or a wrong conflict choice leaves no copy.
  • No record of what went wrong on someone's machine. Only the updater writes a log; script errors go to a console nobody sees. The v0.30.1–v0.30.3 text-resize hunt needed you to paste console snippets.
  • Licences and policies are incomplete. No third-party notices for the ~400 bundled packages, SECURITY.md still says 0.12.x is the supported version, no issue templates, no privacy statement for the web app's OneDrive access.
  • Testing stops at the mock. The real window, the updater, upgrades between versions, large folders, contrast themes and screen readers are checked by hand or not at all.
  • The installers are unsigned (parked by you), and the README lists macOS and Linux build prerequisites for builds nobody has made.

A · Trust and distribution

What a careful person checks before installing an app that holds their notes.

A1

Code signing: keep parked or revisit

Now

Unsigned installers. Windows SmartScreen shows "Windows protected your PC" to every new user, and Smart App Control blocks the installer and the in-app updates outright (your second laptop, os error 4551). You parked signing on 2 October; the researched options (SignPath for open source, an OV certificate, Azure Trusted Signing, the Microsoft Store) are in memory.

Proposed

No work unless you say so. This card is here because, for strangers, it is the single largest barrier to installing ChronoNote, larger than anything else on this page. "Approve" means: reopen the comparison and pick one. "Reject" means: keep parked, and E3 documents the SmartScreen "More info → Run anyway" step instead.

A2

Third-party licence notices

Now

The installer ships Tauri, CodeMirror, Svelte and roughly 400 Rust crates. Most are MIT or Apache-2.0, which require their copyright notice to travel with the binary. Nothing in the repo, the installer or the About tab carries them.

Proposed

Generate THIRD-PARTY-NOTICES.txt at release time from cargo-about (Rust) and license-checker (npm, production dependencies only), bundle it as a Tauri resource, and add "Open-source licences" to the About tab, which opens it. A CI step fails if a dependency arrives with a licence outside an allow-list (MIT, Apache-2.0, BSD, ISC, MPL-2.0, Zlib, Unicode).

Cheap legal hygiene, and the allow-list also stops a copyleft dependency from slipping in through Dependabot.

A3

Current SECURITY.md, issue templates and a "Report a problem" link

Now

.github/SECURITY.md lists 0.12.x as the supported version. There are no issue templates, so reports from strangers arrive without a version, Windows build, scaling or language. The app has no route to report anything.

Proposed

  • SECURITY.md: "the latest release" instead of a version table, so it can't go stale again.
  • Templates in .github/ISSUE_TEMPLATE/: Bug (version, desktop or web app, Windows version, display scaling, language, steps, expected, actual, the C1 diagnostics block), Feature request, Translation issue; blank issues off.
  • About tab: "Report a problem" opens the Bug template with the version pre-filled in the URL. No personal data in the URL.
A4

Privacy statement

Now

The web app asks for access to the user's OneDrive (read and write files, keep signed in). The desktop app checks GitHub for updates. Neither the website nor the app says what is collected, where notes live, or what the OneDrive permission is used for.

Proposed

A short website/privacy.html, linked from the website footer, the About tab and the OneDrive sign-in step: no telemetry or analytics; notes stay in your folder, your browser (IndexedDB) or your own OneDrive; the update check sends only a request for latest.json to GitHub; the OneDrive permission is used only for the chosen notes folder; the sign-in token is kept in the OS keychain or browser storage and removed on sign-out; how to delete everything.

Microsoft's app registration also expects a privacy link once people outside your organisation sign in.

B · Never lose a note: recovery

Prevention is strong. These add a way back for the cases prevention can't cover: a user's own mistake, and bugs nobody has found yet.

B1

Recently deleted: a trash folder for removed notes

Now

A dated note whose tab closes while empty is deleted from disk (#63, §169). On the web app, deletes go straight out of IndexedDB and are pushed to OneDrive. If the note was emptied by mistake (select all, delete, close), it is gone.

Proposed

Every delete moves the file to .chrononote-trash/<date>_<filename> in the notes folder (an IndexedDB store on the web app), and anything older than 30 days is removed at startup. Settings → Notes gets "Recently deleted": a list with Restore. An empty file is not worth keeping, so only files that had content on disk go to the trash; the #63 behaviour for truly empty notes stays as it is.

B2

Earlier versions of a note

Now

Overwrites that are not the user's own typing leave no copy: import with Replace, a conflict resolved with "Keep mine", a newer file from OneDrive taken over an open tab, the copy-forward rewrite of a source note.

Proposed

Before any such overwrite, and at the first save of each day, keep the previous text in .chrononote-versions/<filename>/<timestamp>.txt; keep 30 days, at most 20 per note. A tab's context menu gets "Earlier versions…", showing the list with a side-by-side preview and Restore (which itself keeps a version first). Plain text files, so they also work outside the app.

Turns a data-loss bug into a minor annoyance. Optional because B1 plus the existing conflict copies already cover the most likely losses; this covers the rest.

B3

Settings survive a downgrade, and carry a version

Now

config.json and the session file have no version number. An older app reading a newer config ignores the fields it doesn't know and drops them on its next save, so going back a version (reinstalling an older installer, or a second PC still on an older release sharing a synced config) silently resets newer settings. Migrations are one-off flags (Peek's defaults_version).

Proposed

Add schemaVersion to both files and keep unknown fields: a #[serde(flatten)] extra map that is written back unchanged. Migrations run by version number in one place. A config newer than the app understands is loaded, kept, and a one-time message says "Settings were saved by a newer ChronoNote; some may not apply". Test fixtures: a real config.json from v0.20, v0.25 and v0.30 must load with nothing lost.

B4

Upgrade test from every older release

Now

Updating is the path every user takes, and it is checked only by you, by hand, on your machines. The mock tests always start from a config the current code wrote.

Proposed

A fixtures folder of real files from past releases (config, session, scratchpad drafts, agenda file, a notes folder with conflict copies and CRLF/BOM files), captured once per minor release by release.sh. Rust and Vitest tests load each and assert the result. Once D1 exists, the native smoke test also starts from the oldest fixture.

C · Diagnosable at a distance

C1

An app log and "Copy diagnostics"

Now

Only update.log exists. Save failures, sync errors, quarantined files and startup time are shown once in the status bar or not at all. Finding the tab-switch resize took console snippets run on your laptop.

Proposed

  • app.log in the app's log folder, rotated at 1 MB × 3: startup timing, errors, failed saves/reads, sync results, quarantines, update steps. Never note text or file content, only file names and error messages.
  • The web app keeps the last 500 lines in IndexedDB.
  • About tab: "Copy diagnostics" copies version, Windows build, display scaling, reduced motion, contrast theme, language, number of notes, enabled features and the last 100 log lines. A3's Bug template asks for it.
  • About tab: "Open log folder" on desktop.
C2

Catch every unexpected error

Now

Nothing listens for window.onerror or unhandled promise rejections, so an exception in a click handler fails silently. The Rust side builds with panic = "abort"; a panic ends the app with no record.

Proposed

Global error and unhandledrejection handlers write to the C1 log and show one status-bar message, "Something went wrong. Details are in About → Copy diagnostics", at most once a minute. A Rust panic hook writes the panic message and location to the log before the abort. Until C1 exists, the handler logs to the console only.

D · Testing where users are

D1

Native smoke tests in CI

Now

Every browser test runs against the mock backend. The real window, Rust commands, the exit barrier, capabilities (the opener and window-destroy permissions both shipped broken once), Peek and the updater are only tested by you.

Proposed

A small suite on CI's Windows runner driving the real release build through tauri-driver (WebView2's Edge driver), against a throwaway notes folder: start, type, wait for save, check the file on disk; close the window and restart, check the session; open Settings and About; trigger a save failure; open a link (opener permission). Ten tests at most, run on every push to main.

This was deferred twice as too heavy. It is the only way to catch the class of bug that has reached you most often: things that only fail outside the mock.

D2

Test under real settings: an environment matrix

Now

The suite runs at 1× scaling, motion on, normal contrast, English, on Linux fonts. v0.30.1–v0.30.4 were all bugs that only showed with another setting: reduced motion, 125–150% scaling, a phone, German on Linux fonts.

Proposed

Extra Playwright projects that run the visual audit, tab switching, menus and Settings under: reduced motion; device scale 1.5; forced colours (contrast theme); German; a 360 px phone. Most are one-line project options. Runs in CI on main only, to keep pull requests fast.

D3

Random-input tests for the parsers and merge

Now

The tokenizer, the three-way merge, line-ending normalisation, list renumbering and paste deferral are pure functions with example-based tests and the golden snapshot.

Proposed

Property tests with fast-check (one dev dependency): the tokenizer never throws and covers every character of a line; merging a version with itself changes nothing; merge is symmetric for non-conflicting edits; normalising twice equals normalising once; renumbering keeps every non-list line unchanged. Thousands of generated inputs per run.

D4

Performance budgets at real sizes

Now

Your work folder has about 180 notes. Startup was measured once (§266). Someone who uses ChronoNote daily for five years has 1,800 notes; a long-running meeting note can reach thousands of lines. Nothing measures search, the Action drawer, History or tab switching at those sizes.

Proposed

A generated dataset of 2,000 notes plus one 5,000-line note, and a CI job measuring: time to a typeable editor, tab switch, search across all notes, Action drawer and History open, typing latency in the big note. Each has a budget about twice today's measurement, so a real regression fails the build and noise doesn't.

D5

Accessibility: automated checks and one screen-reader pass

Now

v0.30 added contrast-theme styles, focus rings and roles, but only one test touches accessibility (the date picker label). Nobody has used the app with a screen reader.

Proposed

axe-core in Playwright over the main screen, every drawer and dialog, the menus and Settings, in light, dark and forced colours; serious violations fail the build. Then one pass with Narrator on Windows: write a note, mark an action done, find a past section, change a setting. Findings become their own fixes.

E · Reach

E1

Platforms: Windows only, said clearly

Now

Only Windows installers exist, and only Windows has been run. The README lists macOS and Linux build prerequisites, and some code paths (Mica, the Snap overlay, Peek's window placement, Zen) are Windows-specific with fallbacks nobody has seen run.

Proposed

Recommended: say "Windows 10 and 11; on other systems use the web app" in the README, the website and the release notes, and move the macOS/Linux prerequisites under "building from source, untested". The alternative is macOS and Linux CI builds plus a check of every Windows-only feature's fallback, published as "experimental": a week or more, and unsigned macOS apps are blocked by Gatekeeper.

E2

Translation status and a glossary

Now

English is the source; Dutch is reviewed by you in use; German, Spanish, French, Italian and Polish were drafted by AI without a native read. Agents have used inconsistent terms (an agent chose "uitgesteld" where the app says "doorgeschoven").

Proposed

The language picker marks unreviewed languages "(community)". A glossary file per language (open, done, deferred, won't do, section, topic, Peek) that briefs and agents must use, and a Vitest check that the glossary terms appear where expected. A3's "Translation issue" template invites corrections.

E3

User documentation: your files, and troubleshooting

Now

The website guide explains the token language and shortcuts well. It doesn't say where files are, how to back up, move to a new PC or uninstall, or what to do when something goes wrong.

Proposed

Two guide pages. Your files: the notes folder and its hidden folders, where settings live, backing up, moving to a new PC, what uninstalling leaves behind. Troubleshooting: the installer or an update is blocked (SmartScreen, Smart App Control), OneDrive conflict copies, a "settings were set aside" message (.corrupt-* files), a global shortcut that doesn't work (another app holds it), and how to send diagnostics (C1).

F · Release process

F1

An early-updates channel

Now

Every release goes to every user at once. v0.30.0 needed four follow-up releases on the same day; with other users, each of those would have reached them too.

Proposed

Settings → About: "Get early updates" (off by default). Those installs also check a latest-beta.json on a rolling pre-release. release.sh --beta publishes there; promoting a beta to everyone is a second, quick command. Large UI releases go to early updates first for a few days, with you and any volunteers on it.

F2

Release script refuses a red build and asks the checklist

Now

CI was red from v0.30.0 to v0.30.2 without anyone noticing. The environment checklist from the v0.30 lessons lives only in my memory.

Proposed

release.sh preflight: refuse when the last GitHub Test run on main failed (override with --force-red and a reason in the notes). For a minor version, print the environment checklist (reduced motion, 150%, phone, installed web app, contrast theme, right-click/long-press/focus) and ask for confirmation. After publishing, wait for the Test run on the release commit and print its result.

G · Plainly missing

Not new ideas: things users of a meeting-notes app ask for in the first week.

G1

Export a note or a range as Markdown or HTML

Now

The files are plain text, and the only export is the app's own bundle for moving between the desktop and web app. Pasting notes into a ticket, an email or a wiki means converting tokens by hand.

Proposed

"Export…" in the More menu and the tab menu: this note, a section, or a date range, as Markdown (sections become ##, actions - [ ] / - [x], deferred and won't-do as struck or annotated items, @name kept) or as HTML with the glyphs. "Copy as Markdown" for a selection.

G2

Print a note

Now

No way to print, or print to PDF, with the glyphs as they appear on screen.

Proposed

"Print…" (Ctrl+P) prints the active note through a print stylesheet: the note only, glyphs in their shapes, section titles as headings, light colours regardless of theme. Windows' own "Microsoft Print to PDF" covers PDF.
