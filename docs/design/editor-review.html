ChronoNote · editor review · 14 November 2026

How solid is editing?

Four Gemini 4 Hydrogen reviewers each took one area: tokens and glyphs, typing and the editing keys, text going in and out (clipboard, saving, outside changes), and the test suite. They reported 42 bugs. I re-ran every one myself with throwaway tests, or read the code where a test wasn't practical. All 42 held up; none was a false alarm.

5can lose text or break the editor. These need fixing first.
17keys and commands that give the wrong text in some caret position or selection
10places where one line means something different in the editor, the counts, export or a menu
10tokenizer edge cases, pasting from Word, Google Docs and web pages, and three tests that can't fail

The verdict

Ordinary typing is in good shape: a line of prose, a bullet, an action, Enter at the end of a line all behave. The bugs sit at the edges, and they cluster for three reasons. Fixing those reasons matters more than fixing the 42 one by one.

  1. The grammar is re-implemented in seven places. The editor uses the tokenizer, but the Actions drawer (glyphLine), the counts, export and print, the line menu, the phone toolbar and withoutLineMarker each have their own regexes. Each copy drifted: # a => v b counts as open in the status bar but Ctrl+J finds nothing; ! urgent @alice by:… loses its name and date in the drawer.
  2. Each key handler was written for one caret position. The handlers assume a caret at the end of a line with no selection. With a selection, a caret before the marker, a line above a title underline, or a §463 held caret, they do something odd. Nothing tests the grid of "every key × every kind of line × every caret position".
  3. The editing commands live inside EditorPane.svelte. So they can only be tested in a browser, one hand-picked case at a time. That is why the suite has 1,429 browser tests and still missed these: the tests are many, but each covers one case.

The test suite is broad but has blind spots. Three state-first tests can never fail: they skip the event type the filter listens to. There are no tests for multiple cursors, IME or dead keys (you type on US-International), the phone toolbar's edits, undo after each command, or byte-exact round trips of CRLF or tab files. There are 82 fixed sleeps in the browser tests.

P1

Fix in four batches, data loss first

Batch 1 as one small PR right away. Then test plan steps 1 and 2 (below) before batch 2: once the commands can be tested in a table, the batch 2 fixes come with tests for every caret position, and the table will find what the reviewers missed. Then batch 3, batch 4, and the rest of the test plan. Each batch is a PR: Hydrogen builds it, an independent tester writes tests from the brief, another model reviews it. Release as 0.38.0 after one beta.

Batch 1 is about 5 small fixes, each with a test that reproduces it. The rest is roughly a week of agent work spread over several sessions.

D1

Ctrl+Z never undoes an outside change

Today

A change from the phone companion, a OneDrive sync or a reload from disk becomes an undo step. Ctrl+Z reverts it, and autosave makes that permanent.

Proposal

Outside changes skip the undo history. Your own earlier undo steps still work: they move along with the outside change, so undoing your typing doesn't touch the phone's edit.

D2

Home stops after the glyph

Today

Home on # (tag) buy milk puts the caret before the glyph. Typing there turns the action back into prose (Z# (tag)…).

Proposal

The first Home goes to where the text starts (after the glyph and any (topic)). A second Home goes to column 0. Same for Shift+Home. This is what code editors and outliners do.

D3

Shift+Enter continues under the text everywhere

Today

Shift+Enter on a bullet, numbered item or topic starts a continuation line aligned under the text. On an action (# , # - , # ! ) or a follow-up (=> ) it goes to column 0.

Proposal

Align under the text on every line kind, the way word wrap already aligns those lines.

D4

Tab and Enter list rules work behind a state symbol

Today

On # 1. item, o - point or v 2. done, Tab and Shift+Tab are plain indents. The numbered-list rules (sub-items, renumbering) only see plain 1. lines.

Proposal

The list rules see through a leading state symbol, so a list of numbered actions indents and renumbers like any list.

D5

Title lines are plain text everywhere

Today

A line above === or --- that starts with # or v is a title for some features (dimming, date links) and an action for others (glyph, counts, Ctrl+J).

Proposal

A title line is never an action or topic: no glyph, not counted. Written in the spec once and applied in the tokenizer, so every feature agrees.

D6

One spacing rule after a marker

Today

# task (two spaces) is an action, => # x is not a follow-up action, and a topic tag is still found after the double space.

Proposal

A marker is the symbol plus exactly one space, everywhere; extra spaces belong to the text. => # x becomes a follow-up action like # task is an action.

D7

A way to write # or v as plain text

Today

Any line starting with a symbol and a space becomes a glyph: a pasted # config comment, v 2.0 released, x = 5. There is no way out.

Proposal

A backslash in front (\# config) keeps the line as text. The editor shows the backslash dimmed; the file keeps it, so it stays readable in any text editor.

Your call: it adds a rule to learn. A lighter alternative is to do nothing and leave a leading space ( # config), which you can't see. I lean towards the backslash, because it is a convention people know from Markdown.

D8

Switch off multiple cursors

Today

The editor allows several cursors (Ctrl+click, Alt+drag), but every ChronoNote command (Enter, Ctrl+1–4, paste merging, list keys) acts on the first cursor only and silently drops the others.

Proposal

One cursor and one selection. Making every command multi-cursor-safe is a lot of work and testing for a feature a keyboard note app doesn't need.

D9

Dragging text follows the paste rules

Today

Dropping dragged text onto an empty # line doubles the marker, and by:tomorrow isn't turned into a date. Ctrl+V does both.

Proposal

A drop goes through the same rules as a paste.

D10

Warn about an impossible due date

Today

by:2026-02-30 or a misspelled by:fridy looks like ordinary text. The action has no due date and nothing tells you.

Proposal

A wavy underline like a spelling mistake, with a tooltip "Not a date". Due words the app will rewrite (by:fri) look as they do now.

D11

A written rule for word moves and double-click around glyphs

Today

Ctrl+Arrow, double-click and Shift+Arrow around a glyph, by: or a (topic) pill each behave as their own code happens to do. None of it is in the spec, and the tests are scattered.

Proposal

A glyph with its space counts as one word; by:date as one word; a topic pill as one word. Written in the spec and covered by the test table (step 2).

Test plan

Based on the test reviewer's plan, with my changes. The aim: every editing rule tested in a table across every kind of line and caret position, quickly, in Vitest, with the browser kept for what only a browser can show.

  1. Move the editing commands out of the component. Enter, Shift+Enter, Ctrl+1–7, section titles, phone toolbar edits and the context menu's edits move from EditorPane.svelte into src/lib/editor/commands.ts, plus a createTestEditor() that builds a real EditorView with the same extensions in the same order. The reviewer checked that the extensions already run in Vitest. Also: only DOM tests get jsdom, which cuts npm test by about 3 minutes of CPU.
  2. The table. Every command × every line kind (empty, prose, bullet, each action state, topic, ! , follow-up, numbered, title, continuation, tab-indented) × caret positions (line start, inside the marker, text start, middle, end, §463 held) × selections (none, inside a line, ending at column 0, across lines). Each row checks the text, the caret, and that one Ctrl+Z restores the exact old text and caret. Roughly 1,000 generated cases in seconds; the expected values are written by hand for each rule, never copied from the code. Fix the three state-first tests that can't fail.
  3. Properties. With fast-check: (a) one line means the same everywhere (editor, drawer, counts, export, menu); (b) open, type, save, reload gives the same bytes for CRLF, BOM, tabs, trailing spaces, no final newline, emoji; (c) outside changes never split a character and keep the caret on its line; (d) dotted numbered lists and mixed tab/space indents.
  4. A small browser suite for what jsdom can't do. IME composition and US-International dead keys (' then e) while typing # , by: and Enter; touch on the phone layout; right-click Paste with HTML; drag and drop; spell check while typing. About 20 tests.
  5. Clean up. Replace the 82 fixed sleeps with polling, and fold the overlapping *.independent.spec.ts files into the table where it now covers them.
  6. CI. Add the remaining pill and alignment specs to the Windows layout job. The reviewer also proposes running the native tests on every PR; I'd keep those on main (slow, and they rarely catch editing bugs) unless you want them.
