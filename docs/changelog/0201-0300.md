## 201. Numbered lists, and numbered sub-lists (v0.12.3)

Item 7 of Marien's next-version list, plus numbered sub-lists (`1.1.`). Plain text, no styling, no rewriting of numbers: the
editor just understands the marker, the way it understands a bullet's indentation.

**What is a numbered item** (`parseNumberedItem`). A marker that is the **first non-blank character of the line**, followed by
whitespace: one or more positive whole numbers (`1` to `999999999`, no leading zero, no zero) joined by dots, ending in `.` or
`)`. So `1.`, `2)`, `10.`, `1.1.`, `1.2.3)`, `2019.` are items (a list may start at any number); `3.5 hours`, `1.5`,
`1.1 not a sublist`, `12 monkeys`, `0.`, `01.`, `a.`, `1:`, `1.` alone (no space typed yet), and anything with text, a bullet or an
action symbol before the number (`- 1. x`, `# 1. x`, `see 1. here`) are not. A marker needs its trailing dot or parenthesis so decimals stay prose.

**Enter** (like a bullet):
- at the end of an item, or with the caret past its marker and space (so mid-item too): a new line with the same indentation
  (spaces or tabs) and the next marker: the LAST number plus one, parents and delimiter kept: `1.` gives `2.`, `9.` gives `10.`,
  `3)` gives `4)`, `1.2.` gives `1.3.`, `1.9.` gives `1.10.`. Mid-item, the tail moves into the new item;
- on an **empty** item (marker only): the list ends, the line is cleared (at any indentation or depth);
- with the caret in the indent or inside the marker: a plain newline (the marker is not duplicated or split);
- on a numbered **section title** (the next line is its `====`): a plain newline, so no number lands between title and underline.
- **Shift+Enter**: a plain continuation line aligned under the item's text (indent plus the marker's width plus one space), no number.

**Tab / Shift+Tab**: the usual two-space indent and outdent; **numbers are never rewritten**, so indenting `2.` under `1.` leaves it `2.`
(type `1.1.` yourself for a sub-list; Enter then continues `1.2.`, `1.3.`). No automatic renumbering anywhere.

**Mixed with bullets and actions.** The marker being the first non-blank character makes the kinds exclusive per line: Enter on a
numbered item continues the numbers whatever bullet lines sit before or after it, Enter on a bullet continues the bullet, a bullet
whose text starts with a number (`- 1. x`) is a bullet, a numbered item whose text starts with a bullet (`1. - x`) is numbered, an empty
bullet and an empty numbered item each exit on their own, and both keep their indentation when nested in the other. A numbered
item is structure like a bullet: `Ctrl/Cmd+1`-`4` leave it alone (prose that only starts with a number, like `3.5 hours`, is still promoted).
It counts as no action and gets no glyph.

Not supported: letters and roman numerals (`a.`, `iv.`), a sub-number without its final dot or parenthesis (`1.1`), automatic renumbering, and a
new marker past nine digits.

Tests: 29 unit tests (`numberedList.test.ts`: every accepted and rejected shape, next markers across digit boundaries and levels, each Enter
outcome including the caret positions and the section-title guard, the Shift+Enter alignment, the promotion exclusion) and 43 Playwright tests
(`numbered-lists.spec.ts`: continuing at any start number and with `)`, 9 to 10 and 99 to 100, exiting at any depth, splitting, the caret before or
inside the marker, Shift+Enter, one-step undo, sub-lists, Tab and Shift+Tab on one line and on a selection, tab indentation, eight bullet/number
mixes, ten lookalikes that stay prose, no glyph and no action count, Ctrl+1, a numbered title, a neighbouring action).

Verification: Vitest 557, `svelte-check` 0, Playwright 374, `cargo test` unchanged.

**Section History take-over bug, found by Marien testing the new destinations.** Reported: "I opened the drawer on a date in the past. When I select lines on that date, I cannot add them to today. - **Symptom 1 (nothing offered from the opened-from note):** wrong when opened from the *past* — "Today" and "Next occurrence" are different files entirely from the opened-from note, so there's something real to forward to. - **Symptom 2 (the silent data loss):** the rule never caught the *mirror* case — browsing *today's own* occurrence while "Today" is offered as a destination is exactly as self-referential (source file === target file), but `isOwnOccurrence` only ever compared against the opened-from filename, not each destination's own target. `commitCopyForward` (`copyForward.ts`) then ran two independent read-modify-write passes — insert into the target section, defer the source range — against the *same* file, each starting from the same pre-edit content. Whichever write landed last won outright, silently discarding the other's edit. **Fix, in two layers.** (1) `HistoryModal.svelte` replaces `isOwnOccurrence` with `usableDestinations` — `$historyDestinations` filtered per occurrence, dropping any destination whose actual target file (`destinationFilename`: `openedFromFilename` for "here", `` `${date}.txt` `` for "today"/"next") equals the *browsed* occurrence's own filename. This is used everywhere the old flag was: the take-over bar, the "nothing to carry this over to" fallback message (reworded, since it's no longer only true for the opened-from note), the footer's `Shift+Enter` hint, and the shortcut itself. (2) `commitCopyForward` hardened as defense-in-depth: when the resolved target filename equals the source filename, it now does one combined edit (insert into the section, then defer the source range *within that same already-updated content* — the insertion always lands after the source range, so the original line indices stay valid) and one write, instead of two independent passes that can race on any path that reaches this function, not just Section History's.

**The full expected-behavior matrix**, worked through and now covered by tests:
- **Opened from today, a future date, or a scratchpad:** the only destination is always "here" — wherever you started. Offered for any occurrence you browse *except* that exact one (nothing to carry a line to when you're already looking at it). Unaffected by whether other sections exist elsewhere — unchanged from before this fix.
- **Opened from a past date, a section already exists today:** `findNextOccurrenceTarget`'s search stops at the first match after the anchor, which is today — so "Next occurrence" is *never* computed at all here, "Today" alone covers it, regardless of whether a further-future section also exists. Browsing the opened-from note or any other past/future occurrence offers "Add to today"; browsing today's own occurrence offers nothing (the only destination there ever was is itself).
- **Opened from a past date, no section today but one exists in the future:** "Today" is always offered (it can create the section); "Next occurrence" is also offered, pointing at that future date. Browsing the future occurrence hides "Next occurrence" (self-referential) but keeps "Today"; today itself never appears in the strip at all here (no section there yet), so there's no way to browse into a "Today" collision in this case.
- **Opened from a past date, no section today or in the future:** "Today" alone, always offered, from every occurrence in the strip (today and the future can't collide with it since neither is present).

## 246. Overview ruler: fixes a native-scrollbar regression from §245, and mutes its marker colors

Marien, right after v0.16.1 shipped: "The overview ruler now forces the default large scrollbars (large and white) to always show horizontally and vertically. Only tabs without actions... show up well, with the smaller scrollbars. But as soon as you add an action the overview ruler triggers and the large scrollbars appear." A real, reproducible regression from §245's new overview ruler — two independent, compounding bugs, both fixed at the root:

1. **The ruler's own box was sized by a JS-measured pixel height** (`this.dom.style.height = trackHeight + "px"`) instead of pure CSS. `.cm-editor` has `overflow: visible`, so any rounding-pixel mismatch between that measurement and `.cm-editor`'s true box escaped it and landed on `#editor-container` — the actual scrollable ancestor (`overflow: auto`), never added to the app's own thin-scrollbar CSS (`.cm-scroller`, `.modal-list`, etc.), so it fell back to a full native OS scrollbar. Fixed by sizing the ruler with `top: 0; bottom: 0;` instead of a measured height — the browser now keeps it pixel-identical to `.cm-editor`'s content box by construction, no measurement possible to get wrong.
2. **The dominant cause**: `.cm-ruler-marker::before` (the touch/click hit-area expansion around each tiny marker) had `right: -2px`, extending 1px past `.cm-overview-ruler`'s own 8px-wide box — and therefore past `.cm-editor`'s own right edge — *unconditionally, every time a single marker exists*, regardless of DPI or window size. `.cm-editor`'s `scrollWidth` counts that 1px overflow regardless of its `overflow: visible`, and it escaped to `#editor-container` the same way. This alone explains "only tabs without actions show up well" and "as soon as you add an action" — `buildMarkers()` returns an empty array with zero markers, so the ruler is `display: none` (no overflow risk at all) until the first marker exists, at which point this fixed, unconditional 1px overshoot appears. Fixed by changing `right: -2px` to `right: 0` — there's nothing to the right of the ruler worth an expanded hit-area anyway, since it already sits flush against the pane's edge.

**Verified as a real bug, not assumed**: wrote a regression test (`overview-ruler.spec.ts`, `"does not force the outer editor container to overflow"`), confirmed it fails against the pre-fix code with exactly a 1px horizontal `scrollWidth`/`clientWidth` mismatch (matching the hand-derived math for bug 2 exactly), then confirmed it passes with both fixes applied — re-run 8+ times to rule out a marginal/borderline pass.

## 264. Numbered lists: Enter in the middle renumbers the items after it (#123)

**Tabs:** stepping opens notes. Leaving Peek returns to the note you started from and closes the notes Peek itself opened, unless you edited them; notes that were already open are never closed. (Closed this way they do appear in "reopen closed tab".)

**Look:** the window is created transparent (`transparent: true`) and the normal window paints the opaque theme colour, so only Peek is see-through; the webview background colour is cleared and restored by `peek_set_transparent`. Only the background layer takes the opacity (20-100%, default 70%); text keeps full strength and gets a soft halo in the background colour. The header strip is hidden by default (an 8 px strip that is still the drag handle and carries the past/today/future colour); "On hover" and "Always" are in Settings. **Other changes this needed:** the plugin is pinned to `tauri-plugin-global-shortcut` 2.3.x because 2.4 requires tauri 2.12, which would have upgraded tauri, tao, wry and about thirty other crates; capability entries for the window calls; the plain-F11 Zen alias no longer fires with Ctrl/Cmd/Alt held; a size read-back in `setBounds` because an undecorated window comes out slightly larger than asked and used to grow on every round trip.

## 277. Peek: one-step resizing of the "On hover" strip, and the window size after Peek from a maximized or Zen window

Two reports from trying v0.23.1:

**1. "On hover" resized in several steps, and worse when the pointer went from the content into the header strip** (the window grew a few times, the bottom edge moved, then settled). Causes, all found by sampling the real window rectangle every millisecond:
- `setBounds` was `setSize` + a read-back + a correcting `setSize` + `setPosition`: three or four visible steps, the first of which grew the window DOWNWARD before the last one moved it up. New Rust command `peek_set_bounds` (`peek_window.rs`) applies position and size with ONE `SetWindowPos`, measuring the window's own frame so no correction is needed. Measured: entering the window is one change (90,243 high -> 69,264 high, bottom unchanged), leaving is one change.
- The intermediate sizes made the browser report leave/enter pairs under a still pointer, which flapped the strip. Collapsing now waits 150 ms and any pointer movement over the window cancels it.
- The strip carried `-webkit-app-region: drag`, which makes WebView2 swallow mouse events over it, so hovering straight onto the thin strip did nothing until the pointer reached the text. Tauri's `data-tauri-drag-region` (already on the elements, and what the main title bar uses) is enough; verified that dragging by the strip and the strip's buttons still work.

**2. Peek from a full-screen window lost the size to come back to.** Two ways to be "full screen":
- *Maximized:* Peek read the window's geometry while it was still maximized (the screen-sized rectangle), put THAT back before maximizing again, and so overwrote what "restore" goes back to: restoring gave an almost-full-screen window. Now the window is un-maximized first and its restore size is read then; leaving Peek sets that size and maximizes again.
- *Zen (fullscreen), maximized or not:* Peek was entered while the window was still leaving Zen and recorded the monitor rectangle as its normal size; afterwards the window was stuck at screen size, not maximized, and "restore" did nothing. Peek now ends Zen and waits until its window changes are done (`whenZenSettled` in `zenWindow.ts`) before it looks at the window.

## 285. Peek fades from in focus to out of focus

## 292. Autosave no longer overwrites a note that changed on disk

**Status: implemented, not yet released.** Review task B.

## 297. Notes with Windows line endings or a byte-order mark work
