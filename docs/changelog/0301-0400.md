## 319. Peek across monitors with different display scaling

**Status: released in v0.29.2.** Marien (2026-10-08): with the full window on a 125 % monitor and Peek on a 100 % one (or the other way round), every Peek round trip made the window on the 125 % monitor larger and the one on the 100 % monitor smaller.

- **Cause:** sizes are remembered and applied in physical pixels with one `SetWindowPos` (`peek_set_bounds`). When that move lands the window on a monitor with another DPI, Windows sends WM_DPICHANGED during the move and the window rescales itself by the ratio of the two scales (x1.25 or x0.8) AFTER our size was applied. The rescaled size was then remembered, so the error compounded.
- **Fix (Rust, `peek_window.rs::place`):** after `SetWindowPos` the outer position and client size are read back; if they are not what was asked, the rectangle is applied again (up to 3 times). The second time the window is already on its monitor, so nothing rescales.
- **Fix (TS, `peekWindow.ts`):** a forced Peek height (fit-to-section / the lines setting) is logical; it was converted with the full window's scale. It now uses the scale of the monitor Peek goes to (`MonitorArea.scale`, `monitorOf`). Unit test added.
- Gates: cargo test 124, clippy clean, svelte-check 0, Vitest 854, Peek/call-note e2e green. **Not verified natively:** this machine has one monitor; needs a check on a two-monitor setup with different scaling.

## 354. The text-resize on tab switch: the reduced-motion rule gave every element a transition

**Status: released in v0.30.3.** Marien's report from §351 ("the text appears larger very briefly and then settles", every tab switch, new in v0.30, on all his machines, also in the web app) was tracked down with measurements he ran on his laptop: console snippets that log, for every frame after a click, the editor's computed font size, line padding and matching rules.
- **The data:** for one or two frames the new editor was 14px (the page's text size, `--type-body`) with 0px line padding (the universal reset) while it matched `.cm-editor`, our `font-size: var(--editor-font-size, 13px) !important` rule existed and the variable was 13px. Only a running CSS transition outranks an `!important` author rule.
- **The cause:** v0.30's reduced-motion rule (§A3, `12-accessibility.css`) set `transition-duration: 0.01ms !important` on `*`. An element without its own transition has `transition-property: all`, so every property change of every element became a transition, and a transition holds the old value until the next frame. When CodeMirror's freshly created editor got its styles (14px → 13px, padding 0 → 6px), the old values stayed visible for a frame or two. It applies only with Windows "Animation effects" off (`prefers-reduced-motion: reduce`), which none of my test runs emulated; that is why nothing reproduced here (not headless, not real Edge, not with a slowed CPU) until the test ran with `reducedMotion: "reduce"`.
- **The fix:** under reduced motion, transitions are now off (`transition-duration: 0s`, `transition-delay: 0s`); animations keep 0.01ms so `animationend` still fires (no code waits for `transitionend`). `reduced-motion-tab-switch.spec.ts` records every frame after three switches with reduced motion on; without the fix it shows `14px 14px 0px` and `13px 14px 6px` frames, as on Marien's laptop.
- **Cleanup of §351's guesses:** the overview ruler's `will-change` (a "text drawn without ClearType" theory) is removed. The opaque `.cm-editor` background stays: harmless and right with Mica. `scrollbar-gutter: stable` from §351 was a real, separate fix (scrollbar-width reflow).

Lesson: a "*" rule with a transition or animation property is never harmless. For layout or rendering glitches that only the user sees, ask early about OS accessibility settings (reduced motion, contrast themes, text size) and test with them emulated.

Confirmed by Marien (2026-10-10): with Windows "Animation effects" switched back on, the laptop no longer flickers on v0.30.2, which matches the diagnosis.

## 394. Docked Peek: cannot be moved, resizes from its bottom, square corners

**Status: released in v0.32.4 (betas 0.32.4-1 to -5 first) (found testing beta 0.32.4-2).**

- **Marien:** resizing docked Peek moved the whole window up, and the next resize moved it back down; the docked window could also be dragged around while the bottom area stayed reserved; and it had rounded corners where a maximized-looking window has square ones.
- **Cause:** §393 only reacted after the fact: a timer 300 ms after the last resize event re-docked at the new height, and nothing followed a move. Windows' own move/resize loop could put the window anywhere in between, and a re-dock that fired during a pause in the drag fought the loop.
- **Fix, native (`peek_dock.rs`):** while docked the window procedure is subclassed. `WM_WINDOWPOSCHANGING` keeps the window full width with its bottom on the strip: a resize from any edge only changes the height (clamped 60 px to half the monitor), a plain move is refused (`anchored`, unit-tested). `WM_EXITSIZEMOVE` reserves the strip again at the final height and emits `peek-dock-height`; a size change outside a mouse drag (`WM_WINDOWPOSCHANGED`, e.g. a keyboard shortcut) does the same. `DWMWA_WINDOW_CORNER_PREFERENCE` = do-not-round while docked, default again on undock (new `Win32_Graphics_Dwm` feature). The frontend's timer re-dock is gone; `peek.ts` saves the height from the event.
- **Checked natively** (isolated debug build, 150%): a move request of 300/400 px was refused; a resize asking for a narrower, taller window kept full width and the bottom at the taskbar, the reservation followed (work area 1192 -> 1083) and the height was saved; leaving and closing restored the screen. Synthetic mouse input from a test process does not reach the window, so a hand drag of the top edge and the square corners still need Marien's check.
