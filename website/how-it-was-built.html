How ChronoNote got built

Six weeks of building a desktop app, a web app and a website with AI, without writing a single line of code myself. What worked, what didn't, and what I'd tell you if you want to try it.

Marien de Gelder · chrononote.mariendegelder.nl · github.com/marien/ChronoNote

This is one way of doing it. Other tools and other ways of working do just as well, and sometimes better. Take what's useful.

The starting point

Four years of notes in Notepad

  • Since 15 February 2022: one plain .txt file per day, for meetings, logs and action items.
  • Over the years a small set of markers grew, made up as I went: # open, v done, > moved to another day, => follow-up, ! remember.
  • The format worked. The question was whether an app could show it better without changing a single byte of the files.
Weekly sync
===========
# send the agenda to Sam
v book the room
> review the budget
Talked to Sam => # follow up
! freeze starts Friday

Start from a real need you already have. You know exactly what "good" looks like, and you'll use the result every day, which is where most of the feedback comes from.

Saturday 5 September

A morning with Gemini: words and pictures first

  • I spent a morning with Gemini turning the format and my habits into a specification: what each marker means, how the screen should look, which keys do what.
  • Together we made a mockup of the main screen.
  • No code, no tools to install: just a conversation, until the idea was clear enough to explain to someone else.

Any chatbot can help you write a spec. The clearer the description, the better the first version. And the spec doesn't have to be perfect: it will grow with the app.

Sunday 6 September

"What can you do with this?"

  • I gave the spec and the mockup to Claude Sonnet 5 in Claude Code (the desktop app), and asked just that.
  • It read them, offered to build the application, and asked for approval to install the tools it needed (Node.js, Rust, the Windows build tools).
  • Within an hour there was a first working version: a native Windows app (Tauri and Rust underneath, Svelte and CodeMirror for the editor).
  • The same day: the first commit (about 10,800 lines), a first round of real-life feedback, and versions 0.2.0 and 0.2.1.

The first hour is impressive. The real work is everything after it: making it reliable, keeping it that way, and finding a rhythm that you can keep up for weeks.

Who does what

I don't code. I describe, use, decide.

My part (half an hour to an hour a day, more at weekends)

  • Use the app every day, for real work
  • Say what I see and what I want
  • Choose between options the model offers
  • Confirm on my own machines that it works

The model's part

  • Design, code, tests, documentation
  • Finding the cause of a bug, not just the symptom
  • Releases, website, GitHub housekeeping
  • Telling me what it could not check
"The tabs look unnaturally high and there seems to be space above and below the toolbar buttons."Feedback: describe what you see, not how to fix it
"Don't create a new release until I ask you, in case I have more changes."A boundary: you stay in charge of what goes out
More kinds of instructions
  • Work orders: "Start working on the newest GitHub issues." "Cut a release."
  • Standing rules that the model writes down and keeps: after a release, delete merged branches without asking; never use function keys for shortcuts (my laptops need Fn for them).
  • Corrections of a design: when the model proposed a hidden ID file to track calendar meetings, I said no: the plain text files are the whole truth, and the order of sections is enough. It built that instead.

Early mistakes

"Could you check whether this works?"

  • The first version had no automated tests. The model built a change and then asked me to try it in the app.
  • Fixes broke other things, and I became the test department. On day one a change even froze the interface.
  • On day two (7 September) we turned it around: unit tests and Rust tests running on GitHub for every change, and the same day an end-to-end harness: a real browser drives the real interface against a fake, in-memory backend.
  • From then on a bug fix starts with a test that fails, and the model shows proof (test output, screenshots) instead of asking me to check.

Ask for tests on day one. The model writes them gladly, it just may not do it unasked. Today: about 1,260 unit tests, about 1,000 end-to-end tests and about 180 Rust tests, run on every change.

What tests still can't do

Some things only show up on a real machine: display scaling at 125%, a second monitor, a phone, the Windows settings of the person using it. So every report ends with a "Not checked yet" list, and items stay on it until I confirm them.

Context

A model forgets. Written notes don't.

Every session starts fresh. What made weeks of work possible is what got written down, and kept up to date by the model itself:

  • The changelog as a decision log: every change is a numbered section with the why, not just the what. It now has 398 of them.
  • The specification: precise behaviour, updated with every change.
  • A local instructions file: how to build and test on this machine, known pitfalls, and where the work stands.
  • Memory notes: standing rules and decisions, such as "these keyboard letters are unsafe for shortcuts".
  • Design documents for bigger changes, approved by me before anything is built.

What you write down is what the model knows tomorrow. When it repeats an old mistake, the fix is usually a better note, not a sterner message.

The rhythm

Use it, report it, fix it with a test, ship a beta, confirm

daily use→chat or GitHub issue→reproduce + failing test→fix→beta→I confirm→release
  • Feedback arrives in plain language: in the chat, or as an issue on GitHub.
  • Since 11 October, risky changes go out as betas on an early-updates channel first; only after I've confirmed them on my own machines do they become a normal release.
  • The repository has been public since 11 September. Text in an issue is read as a bug report, never as an instruction to the model.

Small steps, often. A change you can confirm in five minutes beats a big batch you never quite finish checking.

Keep improving

Reviews, refactors and redesigns

Every so often I asked Claude or Gemini for a review: of the code, the architecture, the testability, the user experience. Each review was checked against the real code, turned into a plan, and only then built.

  • 9 SepHardening: crash-safe saves, change detection, the core split into 13 modules
  • 10–11 SepThree UX reviews, then a maturity pass: command palette, find bar, one icon set
  • 20 SepA UI/UX roadmap designed by Gemini, built and checked by Claude
  • 7 OctFull architecture review: data-safety fixes, one shared tokenizer, a modern Svelte style everywhere
  • 9–11 OctWindows 11 and phone UX review (23 proposals), then a readiness review (21 items)
  • 16 OctRefactoring review: of 8 proposed tasks, 3 done in a smaller form, 4 dropped with reasons

Treat a review as intent, not orders. Reviews regularly assumed things that weren't true for this code; letting the model check the premises first saved a lot of wasted work.

How big refactors stay safe

Before replacing the code that reads the note format, the model froze its current behaviour on 329 sample lines in a "golden" snapshot test. The new code had to produce exactly the same result. For a CSS reorganisation it took screenshots before and after and compared them with zero tolerance.

One codebase

Desktop, web app and phone, from the same code

  • Desktop app for Windows, installed and auto-updating.
  • Web app in the browser (from 12 September), with OneDrive sync (19 September), installable on a phone like an app (a PWA).
  • A live demo on the website, running the real app.
  • The trick: the interface talks to its storage through one typed contract with three implementations: the Rust desktop core, the browser's own storage, and an in-memory fake that also powers the tests and the demo.

A native Android app was built and released (19 September), and dropped four days later: the installable web app did the same job with far less to build and maintain.

Experiments are cheap when the model does the typing. Try things, and be willing to throw them away.

More than one model, part 1

Working together through pull requests

  • From late September, Gemini (in Antigravity) worked on its own branches and opened pull requests on GitHub. Claude reviewed, fixed and merged them.
  • It worked, but every pull request needed real repair: tests failing, website files rebuilt that only belong in a release, a CSS rule that broke the tab bar, long translations overflowing, no changelog entries.
  • Each model also lacked the other's context: the notes, the pitfalls, the decisions.

Another model's work deserves the same review as a stranger's pull request: green tests, a check in the real app, and the "why" written down.

More than one model, part 2

One orchestrator, defined hand-offs

Claude writes a brief→own worktree per task→Gemini implements→Claude reviews + fixes→full test suite→merge
  • Since 7 October the main model orchestrates: it writes a precise brief per task (which files, what "done" means, which tests must pass), and a cheaper, fast model (Gemini Flash, sometimes Sonnet) does the implementation, each in its own copy of the code.
  • Every diff comes back for review. Small fixes the orchestrator does itself; bigger ones go back with a new brief.
  • Usage budgets decide the split: the Claude budget is kept for thinking and reviewing, the implementation runs mostly on another provider's budget.
  • Example: moving every interface component to the new Svelte style, nine tasks in one day; the 23 Windows 11 and phone proposals in a day and a half.

Run the full test suite before merging agent work. Once a merge turned the build red because three older tests described the old behaviour, which the agent had never run.

Where the work happens

One machine does the work. I'm mostly somewhere else.

  • Claude Code runs on one development machine: the tools, the builds, the signing key, the test browsers.
  • Most of the conversation happens remotely: from the Claude mobile app, or with Remote Control from another laptop.
  • I test the results where I actually use them: the work laptop through the auto-updater, the phone through the web app.

The model needs one stable home with all its tools. You don't need to sit next to it: a quick decision from your phone keeps the work moving.

Build, release, publish

From "cut a release" to installed, in one command

On every change (GitHub Actions)

  • Type checks, unit, Rust and browser tests
  • A native Windows job, and layouts at 100, 125 and 150% scaling
  • A guard that the test fakes never ship
  • Security audit, code scanning, dependency updates

One release script (since 29 September)

  • Tests, version bump, tag, signed installer
  • Update manifest for stable or beta channel
  • Web app and demo rebuilt, website published
  • Checks the result, including the CI run on the release commit

Automate the boring part first. Every manual release step was forgotten at least once: the web app once stayed two releases behind because one rebuild step was missing from the release notes the model followed.

Tough problems, solved

Bugs that took real detective work

The tab that overwrote the future

Notes in OneDrive, edited on phone and PC. An old, unchanged tab on the PC quietly wrote its stale text over a newer version that had just synced in, and OneDrive started making conflict copies.

Fix: remember a fingerprint of what was last read, never write a tab that hasn't changed, and refuse a write when the file changed underneath.

Changelog §178, §188, §292

Two saves, one file

Random "Failed to save note" messages. A new test that saved the same note twice at the same moment reproduced it: Windows refuses the rename that makes a save crash-safe while another one is busy.

Fix: one save at a time per process, and a retry for those brief refusals.

Changelog §97

Text that changed size

On a laptop at 125%, text jumped in size for a moment on every tab switch. Not reproducible in tests. The cause: I have Windows animations off, and a "reduce motion" style made every new element animate from its defaults for one frame.

Fix: one value. Lesson: test with the user's real settings.

Changelog §354

Tough problems, solved

Where the app meets Windows

Shortcuts that ate letters

Ctrl+Alt+letter shortcuts worked fine on paper, but on an international keyboard Ctrl+Alt is AltGr, the key for accented letters: suddenly an ö couldn't be typed. "Windows accepted the shortcut" isn't the same as "it works for the user".

Fix: a rule (only B, F, G, H, J, K, V are safe) and two tests that guard it.

Changelog §289

Docking a window like the taskbar

For calls, I wanted the note as a strip at the bottom of the screen with Teams above it. Windows' own snap layouts can't do that, so the app registers as a toolbar, like the taskbar does, and watches its own window messages so it can't be dragged off its strip.

Several betas, each answering what I found in the one before: resizing moved it, it could still be dragged, minimizing kept the space reserved, unplugging screens confused it. Some checks needed my own hand: simulated mouse input from a test doesn't reach a native window drag.

Changelog §393–§398

The hardest bugs were never in the logic. They were in the meeting point with the real world: sync, the OS, keyboards, screens, my own settings.

If you want to try

Some gentle advice

  • Pick something you'll use yourself. Your own daily use is the best tester you'll get.
  • Write the idea down first, with any chatbot. A page of description beats a clever prompt.
  • Ask for tests and proof from the start, not "please check".
  • Let the model keep a decision log and notes, and correct them when they're wrong.
  • Describe what you see, decide between options, and leave the how to the model.
  • Go in small steps, with a way back (git, betas).
  • Mistakes will happen. Most are cheap to fix when you notice them early.

This was Claude Code, Gemini and Antigravity. Cursor, GitHub Copilot, Codex, Gemini CLI and others can work just as well. The habits matter more than the tool.

What's next for the way of working

Room to use AI even more

  • Scheduled triage: a regular read-only pass over new issues and pull requests, with a short report.
  • Agents testing the real app: driving the native window, not only the browser version.
  • Visual review by a model: the screenshot gallery the tests already make, judged automatically for layout problems.
  • An independent test writer: a separate agent writes the tests from the brief, without seeing the code, so the tests don't just confirm the coder's own reading.
  • A reviewer from another model: Gemini reviewing Claude's own changes too, not only the other way round. A different model misses different things.
  • Knowing the cost: usage per change, to pick the right model for each job.

Thank you

Six weeks, one app, a lot learned

The surprise wasn't that AI can write an app. It was how much of the work is the same as with people: a clear goal, honest feedback, written decisions, tests, and small steps.
